# Workspace shell: modules, business objects, document flow and their accounting — evidence

> **Feature:** `DJERP-016` (with `DJERP-017`, `DJERP-018` and `DJERP-013` seen through it) · **Scenario:** `verify/scenarios/workspace-shell.yml` · **Generated by:** `node verify/runner.mjs --only workspace-shell,simulation-console,smoke-home` against a fresh database on `http://127.0.0.1:8766`, plus signed-in captures from a seeded sandbox on `http://127.0.0.1:8765`, both on 2026-11-21 (UTC) · **Result:** PASS on desktop and mobile

A visitor opening `/app/` on a fresh database, and then a deep link into a document (`/app/sales/orders/1/?tab=flow`), gets the same shell (`data-page="app"`) both times: a labelled sign-in usable from the keyboard ("Sign in to DjangoERP"), the module navigation, global search and page area hidden until there is a session, the skip link as the first Tab stop, the deep link's URL kept for after sign-in, and a refused sign-in reported in the form ("No active account found…"). All 30 steps passed at 1280×800 and 390×844, with no console errors and no horizontal scroll.

The first run failed at the skip-link step, on both viewports and in the console's scenario too: the shared sign-in autofocused the username field on page load, so the first Tab went to the password field. The shell now focuses the form only after an in-page sign-out or an expired session. Capturing the signed-in screens below found three more defects, all fixed before these images were taken: a list's sticky table header sat 52 px down inside its horizontally scrolling wrapper and covered the first row (an `overflow-x: auto` box is a scroll container on both axes, so the header no longer sticks); a shipment's flow card showed the audit row's wall-clock date instead of its stock moves' business date (`workspace/tests.py` now back-dates the moves and pins it); and posting an invoice toasted "Invoice … created" a second time (a response that is the acted-on document now reads "Post to ledger: done.").

## How the signed-in captures were made

A scratch SQLite database was seeded with `python manage.py simulate --ticks 55 --start 2027-01-01` (the agent sandbox, so every document was created through the ERP's services), then the console evidence session stepped it to tick 62. Four throwaway accounts exist only in that file — `analyst` (accountant), `viewer`, `auditor` and `boss` (admin) — so no real credentials were used (`verify/verify.yml` `agent.never`). A Playwright session at 1280×800 then:

- opened the home page: 12 work-queue tiles, the quick-create buttons and every module with its record count;
- opened the invoiced sales orders as a filtered link (`?status=invoiced`, 188 records at the time) and the newest one, SO-00184, on each tab: its lifecycle stepper (Draft → Confirmed → Partially shipped → Shipped → Invoiced), its document flow chain SO-00184 → SHP-00184 → INV-00184, its two journal entries (shipment and invoice, both "✓ Balanced"), its three stock moves, and its history;
- searched from the header with the keyboard (`/`, "A-WIDGET", ↓, Enter), landing on the product and its flow;
- opened a confirmed work order (WO-00111) with its component availability, and the balance sheet ("✓ Balanced");
- ran order to cash through the screens: a new sales order for Retail Chain Ltd (1 × A-WIDGET-XL at 220.00), Confirm, Ship, Create invoice, Post to ledger. The toasts read "Sales order SO-00191 saved.", "Confirm: done.", "Shipped as SHP-00189.", "Invoice INV-00189 created. Open" and "Post to ledger: done."; the invoice's entry debits 1100 Accounts Receivable and credits 4100 Sales – product line A for 220.00; the order ended "Invoiced" with the chain SO-00191 → SHP-00189 → INV-00189;
- signed in as each other role. The viewer's navigation listed 20 items and no transactional documents; opening `/app/sales/orders/` said "Your role (viewer) cannot read sales orders. The API allows: admin, accountant." The auditor's listed 24, including financial statements, invoices and payments but not journal entries ("Your role (auditor) cannot read journal entries. The API allows: admin, accountant." — the API's own rule: auditors read journal lines, not entries), and the income statement page offered no write buttons. The admin's home showed the activity feed (15 rows), and SO-00184's history listed its three audit events (confirm, ship with the shipment, entry and move numbers, invoice);
- signed in again on an iPhone 13 viewport in dark mode, opened the purchase orders and the navigation drawer.

Across the session there were no page errors or console errors, and no horizontal overflow at 1280 or 390 px. The record numbers above are from the run that produced these images; earlier runs against the same file had already created SO-00187 to SO-00190.

## Not covered

- Editing and deleting a draft were not exercised in this session; each app's API tests cover the rules the Edit and Delete buttons rely on (drafts only, `ProtectedHistoryDestroyMixin`), and the buttons only appear when the registry's `editable` statuses and the role's write access allow them.
- Purchase-to-pay and make-to-stock were not walked through the screens in this session; the simulation agents drove them through the same services, and their documents' flow, accounting and stock tabs render from the same read model as the sales order's.
- Screen readers were not run; the checks were structural (labels, roles, `aria-current`, `aria-sort`, `aria-expanded` on the search and menu, the skip link, focus on sign-in).
- Docker and PostgreSQL: SQLite and `runserver` only.
